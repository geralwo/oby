# tree-sitter-oby

A [tree-sitter](https://tree-sitter.github.io/) grammar for OBY, with the
queries Zed uses for highlighting, bracket matching, the outline, and
indentation.

It is written from `src/compiler/parser.c` and `src/compiler/lexer.c` — the
compiler is the specification, not the prose docs. The grammar's header comment
explains the three things that shape it (newline handling, contextual keywords,
and why types are written as expressions).

## Checking it

```sh
npm install                  # tree-sitter-cli, once
npx tree-sitter generate     # grammar.js -> src/
npx tree-sitter test         # test/corpus/
```

The corpus is small; the real check is the compiler's own source, which the
grammar must parse without a single error node. Every *valid* file under `src/`
and `tests/` is one of those — `examples/` is working space and is not a
criterion (it happens to parse too):

```sh
for f in $(find ../../src ../../tests -name '*.oby'); do
  n=$(npx tree-sitter parse "$f" 2>/dev/null | grep -c ERROR)
  [ "$n" -gt 0 ] && echo "$n $f"
done
```

A file named `*_error.oby` is *meant* to be broken — those are the compiler's
negative tests — so errors there are expected. Everything else should be clean.

## What the grammar does not do

Two rules here are stricter than the compiler, both because a parser without
unbounded lookahead cannot do what the compiler does by rewinding:

- **A type argument list is written tight.** `Box<int>` is type arguments; `i <
  5` is a comparison; a comparison spelled tight (`i<5`) reads as the start of
  type arguments and reports an error.
- **A statement that starts with a name reads as a binding when a name follows
  it** (`Point p = {}`), which is what the compiler picks too.

`X = type { ... }`, `X = enum { ... }` and a type alias are ordinary assignments
whose value is a type expression here, where the compiler has dedicated
statement nodes. The queries read the value's node kind instead.

## Wiring it into an editor

Zed loads a grammar through an extension's `extension.toml`, which names a
repository, a revision, and where inside the clone the grammar sits:

```toml
[grammars.oby]
repository = "https://github.com/geralwo/oby"
path = "editors/tree-sitter-oby"
rev = "<a commit of that repository that has this directory>"
```

`rev` is why the work is committed before the extension can reach it: Zed checks
out that commit and builds from the tree it finds there, so a `rev` older than
the grammar itself has nothing to build. With `path` the grammar needs no
repository of its own — but note that `src/parser.c` is committed here rather
than generated, because Zed compiles it with clang and never runs the CLI.

A `file://` URL works in place of the HTTPS one for a purely local setup.

For Neovim and Helix, which fetch a grammar by repository without a `path`, the
directory would have to be a repository with the grammar at its root.

The queries:
- `queries/highlights.scm` — syntax highlighting
- `queries/brackets.scm` — bracket matching and rainbow brackets
- `queries/outline.scm` — the outline panel
- `queries/indents.scm` — auto-indentation

## Layout

```
grammar.js           the grammar
queries/*.scm        the four query files above
test/corpus/oby.txt  tree-sitter test cases
src/                 generated by `tree-sitter generate` (committed: Zed
                     compiles `src/parser.c` and never runs the CLI)
```
